# 编排游戏脚本

目标：用 `pipeline_draft` 做出一条用户看得懂、电脑带得动、一个游戏出错不拖累其他游戏的流水线草稿。

## 规则

- **用本应用的流水线工具**：`script_list`、`script_tasks`、`system_info`、`pipeline_list`、`pipeline_get`、`pipeline_draft`、`pipeline_run`。不要用 `workflow`、`schedule_create` / `schedule_update` 之类的通用工具来编排游戏，它们不会排队资源，也不会出现在「编排」页。
- **先看硬件再并行**：资源不冲突（不抢鼠标、不抢同一台模拟器）只说明不会互相干扰，不说明电脑带得动。每个游戏客户端都吃 CPU、显卡和内存，模拟器本身还要 3–4 GB 内存。并行之前一定先调用 `system_info`，按它的建议决定；没法判断时就串行。
- **不改脚本、不擅自运行**：只用脚本现有的任务和配置；草稿做好后告诉用户，等用户说再运行或设定时间。
- **说清依据**：告诉用户为什么这样排（硬件、资源、先后关系），哪些是你确认过的，哪些没确认（例如某个脚本跑完会不会自己关游戏）。

## 步骤

1. `script_list` 找到用户说的脚本；对每个脚本 `script_tasks` 看有哪些任务、参数、用什么资源（模拟器 adb / 前台鼠标键盘 desktop / 后台窗口 window / 不占 none）。用户没说任务时选「日常」类任务，并在回复里说明选了哪个。
2. `system_info` 看 CPU、内存、显卡。按 `advice`：
   - 内存 16 GB 以下、没有独立显卡，或拿不到信息 → **全部串行**。
   - 内存 16–32 GB、有独显 → 默认串行；用户想快可以「一个模拟器游戏 ∥ 一个 PC 游戏」。
   - 内存 32 GB 以上、独显 8 GB 以上 → 可以「一个模拟器游戏 ∥ 一个 PC 游戏」并行；两个以上 PC 游戏不要同时开。
   - 同时用鼠标键盘（desktop）的任务永远不能并行；画成并行也会自动排队，但串行画出来更清楚。
3. 排顺序（串行时）：
   - 同一台模拟器上的任务放在一起连续跑，最后勾「结束后关闭模拟器」。
   - 先跑耗时短、容易失败的（例如需要登录的），把长任务放后面；用户有偏好就按用户的。
4. 连线：串行时每一步到下一步用 **`when: always`（上一步结束后，不管成败）**，这样一个游戏失败不会让后面的游戏都不跑；只有用户明确要求「失败就停」时才用 `success` 或 `then: stop`。最后一个任务连到一个 `notify` 节点发汇总。不需要自己加「开始」「结束」节点，系统会加。
5. 失败处理：默认不重试（游戏脚本自己多数会重试）；用户在意成功率可以 `retries: 1`。
6. `pipeline_draft` 提交（id 用小写短横线，如 `daily-games`）；看返回的 `check`：有 error 就改正重交；有「会自动排队」的 info 说明画了不必要的并行，可以改成串行。
7. 回复用户：顺序（A → B → C → D）、为什么这样排、预计时长（`check.estimateMinutes`）、没确认的事项；问要不要现在运行一次（`pipeline_run`）或设定每天的时间（在「编排」页保存后设置）。

## 例子

四个游戏（鸣潮 ok-ww 后台窗口、终末地 MaaEnd 前台、星铁 三月七 前台、明日方舟 MAA 模拟器），电脑 16 GB 内存、核显：

- 串行：鸣潮 → 终末地 → 星铁 → 方舟（模拟器放最后，跑完关模拟器）。
- 连线全是 `always`；最后 notify「今天的日常跑完了」。
- 回复里说明：内存 16 GB、没有独显，所以一个一个跑；某个游戏失败不影响后面的；各脚本跑完是否关游戏取决于脚本自己的设置（列出没确认的）。

## 出了问题

- shell 命令在沙箱里失败（退出码 3221225794 / 0xC0000142、`SANDBOX_UNAVAILABLE`）时不要反复重试同一条命令：硬件信息用 `system_info`，脚本状态用 `script_runs`、`script_run_log`；确实需要 shell 时，用 `sandbox_permissions` 加 `justification` 请用户批准一次。
- 回复里只写工具确认过的事实；工具失败就如实说明是哪个工具、什么错误。
